## 1. Резюме для руководства (Executive Summary)

**Что предлагается.** Развернуть уже написанный ИИ-агентами сервер магазина (проект `kompmaster-server`: Node.js + Express + PostgreSQL + S3-хранилище; 33 файла исходного кода, регистрация с SMS-подтверждением, заказы с защитой от «гонки» остатков, идемпотентный приём платёжных вебхуков, модерация отзывов, Telegram-уведомления — код в репозитории, commit `db67caa0`) в интернете «как есть», собрать за 3–4 месяца реальные данные о покупателях, а затем перестроить технический «скелет» в переиспользуемую white-label платформу (одна техническая основа, на которую «надеваются» разные бренды, дизайны и домены), чтобы каждый следующий магазин запускать за дни, а не за месяцы.

**Ключевая особенность модели затрат.** Платной команды разработчиков нет — всю работу выполняют ИИ-агенты (программы на базе больших языковых моделей, которые пишут код и настраивают серверы) под управлением одного человека-владельца. В смете **нет строк «оплата труда разработчиков»**. Владелец не имеет опыта разработки, поэтому качество обеспечивается не его экспертизой, а **процессом**: каждое задание агенту оформляется как письменная спецификация, а принимается — по автоматически запускаемым тестам (Spec & Test Driven Development). Это бесплатно (инструменты с открытым кодом) и снимает главный риск «неопытный владелец + ИИ».

Для сравнения: отраслевые оценки содержания малого интернет-магазина силами людей — **$5 000–15 000 в год** только на поддержку ([Adevs, 2026](https://adevs.com/blog/software-maintenance-costs/)). Наша модель: **~$972/год «всё включено»** ($81/мес.).

**Главный стратегический вывод.** Вложение **$240** (рефакторинг $200 + оценка open-source $40) окупается **уже при запуске второго магазина**: экономия на одном повторном запуске ~$813 (стоимость магазина с нуля $913 − стоимость запуска на платформе $100). При пяти магазинах суммарная экономия ~$3 252 (ROI ≈ 1 255%, расчёт — раздел 11).

## 2. Обязательные термины простыми словами

| Термин | Простое объяснение |
|---|---|
| **PoC (proof of concept)** | Демонстрационная, «черновая» версия магазина: работает по-настоящему, но без излишеств. Цель — проверить спрос и собрать уроки дёшево. |
| **White-label** | Одна техническая «заготовка» магазина, на которую наносятся разные бренды: логотип, цвета, домен, каталог. Как один и тот же дом с разными вывесками. |
| **ИИ-агент** | Программа-«цифровой сотрудник», которая по заданию человека пишет код, настраивает серверы, ищет ошибки. Оплачивается подпиской ($20/мес.) или по объёму работы (токенам). |
| **Токен** | Единица измерения работы ИИ-модели (примерно ¾ слова). Цены указываются за 1 млн токенов. |
| **Spec & TDD (спецификация и тест-драйвен разработка)** | Порядок работы, при котором сначала письменно описывается «что должно получиться» (спецификация) и пишутся автоматические проверки (тесты), и только потом ИИ-агент пишет код. Владелец принимает работу **по отчёту тестов**, а не по чтению кода. Это главный инструмент качества для человека без опыта разработки. |
| **Плацдарм для ИИ-агентов** | Подготовленный набор инструкций и «правил игры» для агентов: файл AGENTS.md (единый стандарт инструкций для ИИ-инструментов, [agents.md](https://agents.md)), шаблоны спецификаций, автоматические тесты, конвейер проверок. Создаётся один раз и используется во всех будущих магазинах. |
| **API (программный интерфейс)** | «Розетка», через которую одна программа получает данные или услуги другой (магазин запрашивает у ЮKassa списание денег). |
| **Вебхук оплаты** | Автоматическое уведомление от платёжной системы магазину: «платёж прошёл». В коде PoC уже реализован идемпотентный приём (повторные уведомления не создают duplicates). |
| **Headless-архитектура** | Магазин разделён на «невидимый двигатель» (товары, заказы, оплата — бэкенд) и «витрину» (страницы покупателя — фронтенд). К одному двигателю можно подключить много витрин — основа white-label. |
| **IaC (Infrastructure as Code)** | Описание всех серверов и настроек текстовыми файлами. Инфраструктуру нового магазина можно «воспроизвести» одной командой, как по чертежу. |
| **SDLC (жизненный цикл разработки)** | Стандартный порядок: план → разработка → проверка → выпуск → поддержка. |
| **CI/CD** | Автоматический «конвейер»: при каждом изменении кода система сама прогоняет тесты и публикует. GitHub Actions — самый распространённый (бесплатно до 2 000 минут/мес., [docs.github.com](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). |
| **ELK** | Промышленный набор для сбора журналов системы (Elasticsearch, Logstash, Kibana). Мощный, но тяжёлый (16–32 ГБ ОЗУ) и дорогой (от $99/мес.) — для бюджетного PoC заменён бесплатными self-hosted аналогами (раздел 6). |
| **Self-hosted (самостоятельное размещение)** | Бесплатные программы с открытым кодом, установленные на ваш собственный сервер вместо покупки облачной подписки. Экономия денег ценой небольшого количества настроек (которые делают ИИ-агенты). |
| **Дашборд** | Экран с графиками и цифрами «на одной странице» для управленческих решений без технических знаний. |
| **Мультитенантность (multi-tenant)** | Режим, при котором одна установленная платформа обслуживает несколько независимых магазинов («квартир в одном доме») с раздельными каталогами, ценами и клиентами. |
| **ФЗ-152** | Федеральный закон «О персональных данных»: базы данных граждан РФ должны находиться на серверах в России (ст. 18(5), [consultant.ru](http://www.consultant.ru/document/cons_doc_LAW_61798/)). Поэтому весь стек — на российском хостинге. |
| **54-ФЗ / фискализация** | Закон об онлайн-кассах: при каждом интернет-платеже покупатель должен получить фискальный чек. Закрывается сервисами эквайера («Чеки от ЮKassa», CloudKassir). |
| **Эквайринг** | Приём безналичных оплат на сайте (карты, СБП, кошельки). Платно только в виде процента с успешных платежей. |
| **Image Search Service** | Сервис автоматического поиска фотографий товаров (по названию/артикулу/EAN), чтобы не фотографировать ассортимент вручную. |
| **Open source** | Программы с открытым кодом: бесплатны, можно использовать и изменять в коммерческих целях (в зависимости от лицензии). |

## 3. Допущения и границы оценки

1. PoC — магазин компьютерных комплектующих/товаров с небольшим каталогом (до ~500 позиций, импорт прайса xlsx/csv уже реализован в коде) и трафиком до нескольких сотен посетителей в день.
2. Жизненный цикл PoC — 6 месяцев; затем решение о запуске полноценной платформы.
3. Единственный человек-оператор — владелец без опыта разработки; его время не тарифицируется. Качество обеспечивается процессом Spec & TDD (раздел 4.4).
4. **Все персональные данные покупателей хранятся в РФ** (ФЗ-152, ст. 18(5), [consultant.ru](http://www.consultant.ru/document/cons_doc_LAW_61798/)) — поэтому выбран российский VPS; зарубежные облака (Vercel, Supabase) для клиентских данных не используются. Бесплатные self-hosted инструменты (PostgreSQL, Grafana, n8n, Metabase и др.) в РФ доступны и применяются без ограничений.
5. Эквайринг: ЮKassa и/или CloudPayments; комиссия — переменная величина (% с продаж), в фиксированную смету не входит.
6. Подписки Claude Pro и ChatGPT Plus оплачиваются через доступные владельцу способы (иностранная карта/сервис-посредник); риск и альтернативы — раздел 12.
7. Цены зафиксированы по официальным прайсам на сентябрь 2026 г.; пересчёт ₽→$ по курсу ЦБ 86,59; возможны колебания ±10%.

**Как работает Spec/TDD-плацдарм (для владельца без опыта разработки):**
1. Владелец формулирует задачу «человеческим языком» → ИИ-агент оформляет её в спецификацию (что должно происходить, что считается ошибкой).

3. Агент пишет тесты, затем код; конвейер GitHub Actions автоматически прогоняет тесты.
4. Владелец принимает работу по отчёту «все тесты зелёные» + ручной проверке сценария в браузере по чек-листу.
5. Все спецификации и тесты сохраняются — это готовый «учебник» для агентов при запуске следующих магазинов (прямой вклад в white-label).

## 7. Рабочий поток №4. Рефакторинг и пересборка «скелета» платформы под white-label

> *Атрибуция раздела: под-агент №4 (open-source e-commerce платформы) и под-агент №5 (IaC/SDLC). Бюджет редакции 2 ужат до минимума: без премиум-подписок, только разовый запас токенов.*

### 7.1. Что делается и когда

После накопления данных PoC (месяцы 3–5) ядро перестраивается в **платформу-конструктор**:

1. **Headless-разделение**: «двигатель» (каталог, заказы, оплата) отделяется от «витрины». Тренд подтверждён: 67% крупных ритейлеров используют headless (Gartner 2026, цит. по [bemeir.com](https://bemeir.com/articles/headless-commerce-architecture-innovation-data-story/)); окупаемость headless-проектов ~18 месяцев ([tenten.co](https://tenten.co/shopify/headless-commerce-trends-2026/)).
2. **Шаблонизация витрины и бренда**: логотип/цвета/домен/каталог выносятся в конфигурацию — новый магазин = новый конфиг.
3. **Абстракция эквайринга**: общий интерфейс платежа с двумя драйверами — ЮKassa и CloudPayments (чтобы для каждого бренда выбирать более выгодную ставку; обе интеграции — открытые SDK/API, лицензионных платежей нет: [yookassa.ru/developers](https://yookassa.ru/developers), [developers.cloudpayments.ru](https://developers.cloudpayments.ru/)).
4. **IaC**: инфраструктура описывается кодом — **OpenTofu** (бесплатно, MPL 2.0, Linux Foundation, [opentofu.org](https://opentofu.org/manifesto)); провайдеры РФ-облаков поддерживают Terraform-API (Selectel — [selectel.ru](https://selectel.ru/services/cloud/servers/vps-hour)); состояние — бесплатно в своём S3. Новый магазин поднимается одной командой.
5. **SDLC-конвейер**: спецификация → тесты → код → автопроверки (Trivy, тесты, сборка) → публикация. Все инструменты из разделов 4–5, все бесплатны.
6. **Мультитенантность**: поддержка нескольких магазинов из одной кодовой базы (выбор платформы — раздел 8).

### 8.2. Рекомендация

**Основной кандидат — Vendure**: «много магазинов из одной установки» — официально документированная базовая функция (каналы + гайд по маркетплейсам, [docs.vendure.io](https://docs.vendure.io/current/core/core-concepts/channels)); минимальные требования к серверу (~512 МБ против 4–8 ГБ у Saleor) — прямо снижает себестоимость каждого нового магазина; один стек (TypeScript/Node.js) с текущим кодом `kompmaster-server` — минимальный «переезд» для ИИ-агентов. Лицензионное исключение для плагинов защищает коммерческую white-label модель ([vendure.io/license](https://vendure.io/license)).

**Запасной кандидат — Medusa (MIT)**: максимально свободная лицензия, готовый шаблон витрины на Next.js ([github.com/medusajs/dtc-starter](https://github.com/medusajs/dtc-starter)); минус — мульти-магазинность требует доработки расширениями.

**Дополнительная стратегия (бюджетная): «растим своё»** — текущий код PoC уже содержит 80% «двигателя» (каталог, прайсы, заказы с защитой остатков, платежи, отзывы, роли). Рефакторинг по разделу 7 может вестись **без перехода на внешнюю платформу** — с заимствованием архитектурных идей Vendure (каналы/бренды как сущности). Это дешевле (нулевая стоимость изучения чужого кода агентами) и сохраняет полный контроль. Решение принимается по итогам оценки (строка 8.3).

Сопутствующие бесплатные компоненты: поиск — Meilisearch (MIT, [github.com/meilisearch/meilisearch](https://github.com/meilisearch/meilisearch)); контент — Payload CMS (MIT, [github.com/payloadcms/payload](https://github.com/payloadcms/payload)); веб-сервер — Caddy/Traefik (Apache 2.0 / MIT — Caddy уже используется в проекте); автопоиск фото — Open Icecat (бесплатный каталог с фото по EAN/артикулам, [icecat.com](https://icecat.com/)).

## 11. Варианты переиспользования PoC для white-label и расчёт ROI

> *ROI (окупаемость) = (Экономия − Вложение) ÷ Вложение × 100%. Все цифры — из разделов 7–9 редакции 2.*

**Базовые константы:**
- Полная стоимость «магазина с нуля» по текущей модели: **$913** (раздел 9.3).
- Стоимость запуска следующего магазина на готовой платформе: **~$100** (домен .ru $2–14 + токены на генерацию конфигурации бренда и каталога ~$60 + стартовый SMS-баланс ~$6 + первичные проверки ~$20; инфраструктура разделяется — вариант B, либо +$12,5/мес. за отдельный VPS — вариант A).
- Инвестиция в платформу (сверх простого PoC): **$240** (рефакторинг $200 + оценка open-source $40).

### Вариант A — «Фабрика шаблонов» (рекомендуется на 1–2 года)

**Суть:** платформа-конструктор; каждый новый бренд = отдельная установка шаблона на своём дешёвом РФ-VPS (свой домен .ru, своя БД, общий код и спецификации).

| Путь (5 магазинов за 3 года) | Расчёт | Стоимость |
|---|---|---|
| Без платформы: каждый магазин с нуля | 5 × $913 | $4 565 |
| С платформой: 1 полная разработка + 4 повторных запуска | $913 + 4 × $100 | $1 313 |
| **Экономия** | $4 565 − $1 313 | **$3 252** |

- Окупаемость инвестиции $240: **при запуске 2-го магазина** (экономия $813 на одном повторном запуске > $240; ROI первого повторного запуска ≈ 239%).
- ROI на 5 магазинов: ($3 252 − $240) ÷ $240 × 100% ≈ **1 255%**.
- Инфраструктура каждого магазина: +$21/мес. (VPS+S3+SMS по прайсам раздела 4.3).
- Подтверждение из отрасли: headless даёт ~80% выгоды «собираемой» платформы при ~40% стоимости ([bemeir.com](https://bemeir.com/articles/headless-commerce-architecture-innovation-data-story/)); окупаемость headless ~18 мес. ([tenten.co](https://tenten.co/shopify/headless-commerce-trends-2026/)).

### Вариант B — «Одна платформа, много витрин» (мультитенантность, рекомендуется с 3-го магазина)

**Суть:** одна установленная платформа (Vendure-каналы или собственная реализация «брендов» по образцу Vendure) обслуживает все магазины: каталоги, цены и заказы разделены внутри одной системы ([docs.vendure.io — Channels](https://docs.vendure.io/current/core/core-concepts/channels); аналогично Saleor: [github.com/saleor/saleor](https://github.com/saleor/saleor)).

| Статья | Стоимость |
|---|---|
| Платформа (включена в PoC-смету) | $913 |
| Доработка до мультитенантности (в рамках рефакторинга; доп. токены) | $150 (разово) |
| Каждый новый бренд: домен .ru + конфиг витрины + SMS-баланс | ~$50 разово × 4 = $200 |
| Инфраструктура: одна на всех; апгрейд VPS до 8 ГБ при 3+ магазинах (Timeweb MSK 80: 1 800–2 000 ₽ ≈ $22/мес., прирост ~$10/мес. × ~24 мес.) | ~$240 за 3 года |
| **Итого 5 магазинов за 3 года** | **≈ $1 500** |

- Экономия против «с нуля» ($4 565): **~$3 065**; против варианта A — ещё ~$200–500 за счёт общей инфраструктуры при 3+ магазинах.
- Предельная стоимость нового бренда: **~$50 разово + $3–5/мес.** доли инфраструктуры.
- ФЗ-152 соблюдается автоматически: все данные всех брендов — на одном РФ-сервере.
- **Риск:** общий сервер = общая точка отказа; меры: ежедневные бэкапы на S3 (уже в смете), Uptime Kuma, почасовая тарификация Timeweb для быстрого восстановления ([timeweb.cloud](https://timeweb.cloud/services/vps-linux)).

### Вариант C — «Клонировать PoC без рефакторинга» (не рекомендуется)

**Суть:** каждый новый магазин — копия черновика PoC без перестройки.

Каждая копия несёт свой технический долг: 20–40% стоимости активов «съедается» долгом ([McKinsey](https://www.mckinsey.com/capabilities/mckinsey-digital/our-insights/tech-debt-reclaiming-tech-equity)); 33% времени — на переделки ([Stripe](https://stripe.com/files/reports/the-developer-coefficient.pdf)); поддержка legacy с высоким долгом — 30–50% от стоимости разработки в год ([Adevs](https://adevs.com/blog/software-maintenance-costs/)).

**Расчёт (5 магазинов, 3 года):** 5 × ($913 − $240) = $3 365 без рефакторинга, но с ростом стоимости поддержки каждой копии на 30–50%/год и независимым исправлением одного и того же бага в 5 копиях → итог ≈ **$4 500–5 500**, т.е. дороже варианта A на **$1 200–2 100** при худшем качестве. ROI отрицательный начиная со 2–3-го магазина.

### Сводная рекомендация

1. **Месяцы 1–4:** строить по варианту A (инвестиция $240 уже заложена в разделы 7–8).
2. **С 3-го магазина:** переход на вариант B (мультитенантность) — предельная стоимость бренда ~$50 + $3–5/мес.
3. **Вариант C исключить** как экономически нецелесообразный.
